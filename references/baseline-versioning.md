# 分类基线的迭代与版本管理

分类不是一次做完的。随着新游戏入库、口径调整、误判修正，基线要一轮轮迭代。
本文定义基线的目录形态、自迭代生成脚本、变更层结构，以及各字段的兼容约定。

---

## 一、基线目录形态

基线是「文档三件套」，每次迭代出一个新目录，**不覆盖上一版**：

```
<你的项目目录>/
  <基线名_YYYYMMDD>/                 每次迭代一个新目录
    <基线名>.md                     人读文档（类目定义 + 成员明细）
    <基线名>.json                   机读基线（权威）
    <基线名>_归属明细.csv            逐款归属明细
    _live原始快照/                   写入时的 live 文件快照
    _vN前备份_<时间戳>.json/.csv     每轮写前备份
  写入前备份_<时间戳>/
```

> 目录名可任意取，**关键是「每次迭代新建目录、不覆盖」**这件事要成立。

变更层另存，按轮次分目录：

```
v9/ v10/ v11/ v12/ v13/ v14/ v17/ v18/ v19/
```

## 二、自迭代生成脚本（重要陷阱）

生成脚本应为**自迭代**模式：读上一版基线 → 叠加本轮变更层 → 输出新基线。

```python
prev = load_baseline(last_dir)      # 读上一版
apply_layers(prev, layer_files)     # 叠加变更层
write_baseline(new_dir, prev)       # 输出新基线
```

> ⚠️ **陷阱：变更层会被重复叠加。**
> 自迭代模式下，若变更层仍留在读取路径里，第二轮会把上一轮的迁移再做一次。

两个修法：

**1. 重放分支** —— 检测基线是否已含本轮特征（如下面已含 `C-Z96`），
自动回退到原始快照重放：

```python
if "C-Z96" in baseline_codes:
    baseline = replay_from(SNAPSHOT_DIR)
```

**2. 快照目录隔离** —— 快照 JSON **无成员明细**，走 CSV 重建；
且**重放时 CSV 也必须读快照目录下的**，否则拿到上一轮结果导致成员重复计入。

> 这是个复合陷阱：只修 JSON 不修 CSV，会得到「成员重复」的新 bug。

## 三、基线 JSON 结构

```json
{
  "文档名": "...",
  "基线来源": "...",
  "统计": { "自建收藏集": 225, "成员合计": 3991, "去重appid": 3991, "跨收藏集重复": 0 },
  "分组统计": { "厂商": {...}, "类型": {...}, "其他": {...}, "动态": {...} },
  "类目定义": [
    { "code": "C-Z97", "name": "C-Z97 厂商-中国联网游戏", "group": "C",
      "成员数":81, "成员": ["<appid>", "<appid>"] }
  ],
  "变更历史": [ { "轮次": "v18", "时间": "...", "说明": "..." } ]
}
```

- `类目定义[].成员` 存**完整成员数组**（不是 diff）
- `变更历史` 逐轮记录增量，可回溯
- 顶层是 dict（注意：live 的云存储文件顶层是**数组**，两者不同）

## 四、变更层结构（键名各轮不同）

各轮迁移条目键名不统一，**渲染端必须全兼容**：

| 轮次 | 迁移条目键名 |
|---|---|
| v9 / v10 / v11 | `真命中` |
| v12 | `新建收藏集[].真命中` |
| v13 / v14 | `迁移计划` |
| v17 | `吸收迁移` |
| v18 | `迁移` |

**渲染端兼容规则：**

```
轮次      固定
时间      时间 | 日期
说明      说明 | 摘要 | 变更
迁移明细  名称 | name
          从   | from
          到   | to
```

> v17 用键名 `迁移`（**不是** `迁移明细`），这是漏兼容的常见原因。

---

## 五、CSV 与 JSON 必须一致

生成后必做**逐条**比对，不是比数量：

```python
csv_map = {row["appid"]: row["归属"] for row in csv_rows}
for c in baseline["类目定义"]:
    for a in c["成员"]:
        assert csv_map.get(a) == c["name"], (a, c["name"])
```

不一致数必须为 0。

---

## 六、基线硬性不变量

每次生成后必查：

| 指标 | 要求 |
|---|---|
| 跨收藏集重复 | **0** |
| 去重 appid | == 成员合计 |
| CSV vs JSON 不一致 | **0 条** |
| 厂商类 / 类型类 / 其他类 | 各自收藏集数与成员数合理 |

## 七、误判修正的教训

**重跑分类脚本会整体重写判定文件，冲掉已固化的人工判定。**

曾发生：重跑分类脚本后收藏集从 219 掉到 213、13 款未归类。

→ 重跑后必须与备份**合并**（以人工判定版为基底，auto 只补基底没有的 key）：

```python
merged = dict(auto_verdicts)
merged.update(human_verdicts)      # 人工判定优先
```

## 八、数据源硬缺陷

**本地 `library_tags.json` 的 `publisher` 只记主发行商，丢弃联合发行。**
涉及「厂商够格立集 vs 落 D 类」的边界判定时，必须查 Steam `appdetails` API 的
`publishers` 数组。详见 `vendor-attribution.md`。

**`step2/app_meta.json` 含 DLC / Tool，不是用户真实库。** 真实库依据是
`library_tags.json`。曾误把月圆之夜 10 个 DLC、桌面精灵工具当游戏加入。

**扫描脚本必须以基线成员集合为真实库边界。** `library_tags.json` 含未拥有条目，
不取交集会扫出假「未归类」。
