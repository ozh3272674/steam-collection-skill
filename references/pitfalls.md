# 实战踩坑清单（遇到异常先查这里）

全部来自真实执行一次"四步全流程"的记录，按步骤分组。

## 步骤1 抓取

| 问题 | 现象 | 解法 |
|---|---|---|
| 游戏详情隐私非公开 | 社区 games 页 302 到登录页；Web API 即使有 key 也返回 0 条 | 用 Cookie（浏览器控制登录提取 steamLoginSecure 是最顺滑的方式）；或建议用户把"游戏详情"改公开 |
| 社区页改版 | 页面 200 且已登录但按旧正则抓到 0 条 | 2025 改版后 `rgGames` 没了，改用内嵌 React Query JSON 数据块解析（`"name"` 与 `"store_url_path":"app/<id>"` 紧邻配对）；两种结构都要兼容 |
| 个人资料装饰品混入 | 解析出 appid 0 / 商城物品 | 过滤 appid 0；`store_url_path` 必须以 `app/` 开头；name 字符集排除 `\` 和 `"` 防跨嵌套误抓 |
| Playwright goto 超时 | 打开社区页 45s 超时但网络正常 | 默认等 `load` 事件被慢资源卡死；改 `wait_until="domcontentloaded"` |
| playwright 装不上 | pip 卡死无输出 | 国内环境：直连清华镜像 **不要套代理**（`pip install playwright -i https://pypi.tuna.tsinghua.edu.cn/simple`）；代理只需给浏览器/请求用 |
| SSL error / EOF | 请求偶发 `SSLEOFError` | 代理节点抖动，脚本带指数退避重试即可 |
| 游戏详情页区域不可用 | 商店页返回"区域不可用" | 换 steamdb 或搜索引擎核实 |
| 系统组件类条目 | manifest 里有 Steamworks Common Redistributables | 系统组件维护一个过滤名单；"有 manifest 但无所有权"的条目（家庭共享残留）只报告不写入 |
| 主会话工具也被限流 | agent 自己的 WebSearch 报 concurrency exceeded | 子代理占满并发时主会话的网络工具同样受限；错峰做自己的搜索 |

## 步骤2 预分类

| 问题 | 现象 | 解法 |
|---|---|---|
| Steam 标签泛滥 | 大量游戏 C 类型 6+ 个、明显不符（动作 FPS 被标"模拟经营+开放世界+战棋"） | 预分类只求覆盖不求精准；步骤3 复核才是质量主力 |
| 兜底类不在最后 | "其他"类排在中间，收藏集列表难看 | 编号规范：兜底用大类内最大号（D99）并与主编号留空档；主编号连续 |
| 编号空位 | 删除/新增类目后 D42 空缺 | 重编号时**单次映射**（43→42, 44→43 … 同一遍扫描），严禁顺序替换（会链式覆盖）；注意 `'D43'.isdigit()` 是 False，要取 `x[1:]` 再判 |
| **兜底判定用「编号以 99 开头」** | 编号改三位补零后，`C099` 被误判成兜底排到最后，而真正的兜底（大类内最大号）反而排错。实测：`C099 厂商-indienova`（7 款，普通类）被错排；真正兜底是 `C167 厂商-中国厂商`（146 款） | 兜底 = **大类内编号最大者**（这才是编号规范的原意，两位时代 99 恰是最大号）。已改为 `fallback_codes()`；类目定义里可显式写 `"fallback": true` 覆盖。排序第三档用**数值**而非字符串，避免位数不一致时 C10 排到 C100 后 |
| 新增类目忘同步 | 部分脚本用旧编号 | 类目定义、规则文件、生成脚本的 NAMES/ORDER 三处必须同一提交里改完 |

## 步骤3 复核

| 问题 | 现象 | 解法 |
|---|---|---|
| 子代理并发上限 | 第 3 个子代理被杀（user concurrency limit exceeded） | 实测上限 2；先双发试探，被拒就回落双路流水线：完成一个立刻补派下一个 |
| 子代理写错分隔符 | 结果文件用 `\|` 而不是逗号；merge 全部漏接 | merge 前跑格式校验脚本（见 methods-review.md），竖线行按 `\|` 重组 |
| 子代理漏空列 | 6 列/5 列行，空值列被省略 | 校验脚本按模式补齐（6 列补 B、5 列补 E+是否确定） |
| 子代理加值前缀 | 字段是 `C=C06;C13` 而不是 `C06;C13` | 校验脚本剥离 `B=`/`C=`/`D=`/`E=` 前缀；`-` 转 `` |
| 子代理上下文爆炸 | 同一批次固定位置崩溃（Model returned no text） | 该批拆两半；提示词加护栏（WebFetch 每款 1 次失败即弃、禁重试、禁中途总结） |
| 子代理中断 | 进程被杀/超时 | 提示词要求每 5 款重写一次结果文件（增量保存）；重派同一批即可续跑 |
| 服务商过载 | Start Plan is busy / quota limit | 等几分钟重试；个别顽固款由主会话亲自搜索兜底 |
| 结果行数对不上 | merge 覆盖数 < 批次总数 | 逐项诊断：未知 appid / 短行 / 列数异常，分类修复后再 merge |

## 增量模式

| 问题 | 现象 | 解法 |
|---|---|---|
| 新装游戏没有 A 状态 | "正在玩/计划玩"收藏集里找不到新游戏 | A 是用户个人状态，detect 后必须问用户或按 categories.md 默认档填进 new_rows.csv 再 merge/apply；apply 会逐条列出"需指定 A" |
| A 状态残留在已卸载游戏上 | 未安装游戏出现在状态收藏集 | apply 自动同步 installed 列并清空 installed=false 行的 A；不要手工只改一列 |
| 新款查不到元数据 | steamcmd 返回 _missing/无 store_tags（测试款/区域限制） | 按名称 WebSearch 分类；仍定不了 C 的进待确认表，不硬编 |
| 标签列是数字 ID | steamcmd 的 store_tags 是 id，批次行不可读 | fetch-info 首次自动抓 populartags 生成 data/steam_tags_map.json 并转换；抓不到（需代理）时保留 ID，子代理按名称自行搜索 |
| 移除的游戏还在收藏集里 | 退款/移除的款仍出现在 Steam 收藏集成员里 | 无害（Steam 忽略不存在的 appid）；要彻底清掉用 `apply --prune` |
| 重复跑增量产生重复行 | 同一 appid 追加两次 | 不会：apply 按 appid 覆盖/追加去重；总表是唯一基准，不设独立 state 文件 |

## 分类质量（实战新增）

| 问题 | 现象 | 解法 |
|---|---|---|
| 泛化类互相吸收 | 每款平均挂 3-5 个类型；「冒险/休闲/合作」装了大半个库 | 跑 `overlap_check.py` 体检；对高重叠泛化类做「准入+排除+锚点」（`category-quality.md`）；只收泛化类，勿全类目一刀切 |
| 属性被当类型 | 「多人合作」与动作重叠 0.34，跟谁都沾边 | 把属性迁成 **F 特性**维度（`C19 多人合作 → F01`），从根上消除互吸 |
| 子代理列错位 | 结果里"依据"写"保留休闲"、判定却填了"冒险" | merge 前抽查"依据↔结论"自洽；**双遍交叉**比对（`compare_passes.py`） |
| 单遍复核不稳 | 同批同口径跑两遍仍有 ~11% 不一致 | 双遍交叉 + 冲突处理三选一（用户拍板/第三遍/多数表决） |
| 标签泛滥 | 商店标签"有就加"导致虚胖 | 标签按**顺序/占比**取（只认前 5 个），而非有/无 |
| 厂商兜底类变垃圾桶 | D99 里混着名厂、中国厂商、长尾 | 见 `vendor-region.md`：联网判国别 + 名厂逐个独立成类 |
| 厂商名判断地区不可靠 | 中文名/英文名都会骗人（`AsicxArt`=成都） | **必须联网核实**；占位串（"本游戏已经下架退市"）不得当厂商 |

## 编号与排序（v4 新增）

| 问题 | 现象 | 解法 |
|---|---|---|
| 编号跟着作品数走 | 按库内作品数降序 + 紧凑连续编号，**新增 1 个厂商就有 157/166（95%）个编号错位**，Steam 里收藏集整体错位 | 改为**字母分桶 + 固定编号**：`C-A05 厂商-Activision`；编号写死在映射表（`v4/code_map.json`），已有永不重排；桶内步长 5 留空档给新成员插队 |
| 兜底类位置不稳 | 兜底按"最大号"算，编号体系一改就漂 | 兜底固定 `-Z99`（Z 桶 + 99，99 不是步长 5 的倍数，永不撞车），恒在大类最后 |
| 收藏集 id 跟着编号走 | 编号一变，Steam 端 205 个收藏集等于整批删掉重建 | id 依据改为**类目纯名**（`厂商-Electronic Arts`）；已存在的类目沿用历史编号，保证写入是"原地改名" |
| 用 `pure[0]` 取大类字母 | pure_name 是 `厂商-XXX`，`[0]` 拿到汉字「厂」，生成出 `厂-105` 这种错编号 | 用前缀映射表取大类（`厂商→C / 类型→D / 其他→E / 状态→A`） |
| 中文名分桶 | 中文首字不是 ASCII 字母，全掉进同一个桶 | 手写拼音映射表（`_v4_sorting.PINYIN`），pypinyin 在本机不可用；未命中的落 `#` 桶（排最前，便于发现漏配） |
| 桶内编号溢出到三位数 | S 桶已有 19 个（C-S05…C-S95），按步长 5 下一个是 `C-S100`，但字典序会把 `C-S100` 排到 `C-S95` **前面** | 步长空档用完后退到 96/97/98 保留位，**编号恒为两位**（`_v4_sorting.SLOT_ORDER`） |

## cloud-storage-namespace-1.json 的三个暗坑（2026-10-10 载荷生成时踩过）

| 坑 | 现象 | 解法 |
|---|---|---|
| **有 `value` 字段缺失的 uc- 条目** | live 里有 6 个 `user-collections.uc-*` 条目**完全没有 `value` 字段**（动态/filter 类收藏集）。若用 `if raw is None: other[k]=v` 兜底，它们会混进 other 侧；而 other 侧只统计非 `user-collections` 的 key → **这 6 条被整体丢弃** | 兜底必须单独存进 `passthrough`，且不论有无 `value` 都原样写回。校验时也要单独归类，不能算进"非收藏集" |
| **系统收藏集没有 added 字段** | 「收藏夹」（`user-collections.favorite`）和「已隐藏」（`.hidden`）有 `value` 但无 `name`/`added`，极易被当"空集"判死而误报 | 校验时把这两类单列，比对**内容 JSON 字符串**是否原样保留，不能参与"空集/成员变化"检查 |
| **动态集 A01 不在基线 CSV 里** | `A01 状态-正在玩` 的成员由 `filter` 决定，`added` 为空 → **归属明细 CSV 里查无此集**。若把它放进 `for nm in members` 循环处理，循环永不执行 → **A01 从载荷里消失** | 动态集必须在循环**之外**无条件写入，循环内 `continue` 跳过。载荷条目总数要与 live 一致才安全 |

## 校验口径的常见自伤（第一版预写校验误报 6 项）

| 坑 | 现象 | 解法 |
|---|---|---|
| 校验「只有目标集合变化」 | 迁移类操作**必然**同时改动来源集合。断言"只有 C-Z96 变化"会误报 26 个 D 类 | 正确口径：①变化集合 ⊆ {目标} ∪ {迁移来源}；②迁移清单里每个 appid 都落到目标；③无意外集合 |

| 迁移会改基线 CSV | 变更层叠加后基线 CSV 已变，用旧 CSV 校验会全盘报错 | 校验必须读**当轮刚生成**的基线 CSV |

## Google Play 识别移动端（2026-10-10 取代旧的关键词扫描法）

| 坑 | 现象 | 解法 |
|---|---|---|
| **Play 搜索页 class 名每次响应都随机生成** | 卡片 class（`Qfxief`/`DdYX5`/`LbQbAe`…）不是稳定字段。按 class 写正则实测 20 款里 8 款解析成"候选 0"，还把 Lumino City 误配到无关 App | 搜索页**只用** `/store/apps/details\?id=` 提取包名；标题与开发者去**详情页**取 |
| 详情页稳定字段 | 详情页没有 `<title>`、也没有 `Offered by` 文本节点 | 用 `<meta property="og:title">`（去掉 ` - Apps on Google Play` 后缀）、`itemprop="name"`；开发者用 `More by XXX` 句式。全部需 `html.unescape` |
| 搜索页无结构化数据 | `AF_initDataCallback` 的 `ds:NN` 数据块数为 0 | 别指望，直接用上面的 HTML 字段 |
| **开发者交叉验证不能作排除依据** | Balatro 的 Steam 开发商是 LocalThunk、Play 发行商是 Playstack，毫无重叠却是同一款游戏 | dev_match 只用于把 STRONG **降级**为 WEAK，绝不用来排除 |
| 搜索结果混入大量蹭词App | 搜 `Guns, Gore & Cannoli` 会命中 `Don Zombie: Guns and Gore`。实测 WEAK 档 448 条里 **392 条（88%）是纯误报** | 必须三档分层：STRONG / WEAK·dev对上 / WEAK·仅蹭词（剔除）。**WEAK 绝不能整批迁移** |
| 第三方移植算不算多端 | Noodlecake / Playdigious / Snapbreak 代理发行的移植版，Play 发行商与 Steam 开发商不同 | 交用户决策（2026-10-10 用户裁定：**算**）

## 分类优先级链（2026-10-10 用户立规）

| 问题 | 现象 | 解法 |
|---|---|---|
| **下级分类掏空上级分类** | The Room 四部曲从 `C-F60 厂商-Fireproof Games` 迁到 `C-Z96 厂商-国外多端游戏`，C-F60 全库仅这 4 款 → 变空 → 被自动清理删除。上级厂商类就此消失 | 铁律：**下级分类的操作不得导致上级分类消失，会导致就不执行**。厂商优先级最高（`C厂商>Z95/96/97/99>D>E`），能归厂商的不再看 Z 类。The Room 正确处置是**留在 C-F60**。详见 `classification-priority.md` |
| 迁移源只认「方案」不认「实际」 | 扫描按方案（D 类口径）做，判定原收藏集写 D-J15；但基线里游戏实际已被收进新建的厂商集。照方案迁出 → 同一游戏同时存在于两个收藏集，跨集重复 > 0 | 迁出源必须取**基线实际归属**，并加断言比对"扫描来源 vs 基线归属"，不一致就告警 |
| 自动清理空集不看成因 | 脚本统一删除成员为 0 的收藏集，把"被下级迁出掏空"和"确实该删"混为一谈 | 空集成因要分开：被下级迁出掏空 → 停下问用户；自然废弃 → 才可删 |

## 通用

- 一切覆盖写操作前先备份（旧表/目标文件），时间戳命名
- 产出 CSV 统一 UTF-8 with BOM（Excel 友好）；agent 内部处理时记得 `utf-8-sig` 读取

## 厂商归属与国别判定（v18/v19 新增）

| 坑 | 现象 | 解法 |
|---|---|---|
| **本地元数据只记主发行商** | Sifu 本地记 Sloclap、官方 publishers 是 `['Sloclap','Kepler Interactive']`；En Garde! / Eternights 同属 Kepler Ghost 白标发行 | 涉及「厂商够格立集 vs 落 D 类」的边界判定**必须查 appdetails API 的 publishers 数组**。并维护子公司映射表（本地名字对不上集名） |
| **子串匹配把厂商判错** | `thq` 把 THQ Nordic 31 款全误判进 Disney（THQ Nordic 属 Embracer，与 THQ 无关）；`nc` 命中 `Inc.`；`snk` 命中 `Snkl Studio` | 集团排查用 **publisher 全名精确匹配**；正则匹配一律用**词边界** `(?<![\w&])...(?![\w])`。实测修正后候选从 152 降到 76，一半是误报 |
| **壳公司马甲** | `KAGAMI WORKs` 实为成都爱相随科技；`NekoNeko Soft` 实为中国 Nekoday | 按「实际开发团队所在地」判，不按法人壳公司 |
| **同名干扰** | `MOR Museum Inc.` 是加拿大温哥华 VR 平台，与东京森美术馆无关；`Shiro Games` 是法国波尔多不是波兰 | 拿不准列「存疑」，不猜 |
| **上市地 ≠ 开发地** | `Bank of Innovation`（MementoMori）是**日本**东证 Growth 4393，中文圈常误认韩国 | 三段记录：母公司注册地 / 子公司注册地 / 实际开发地 |
| **规则 ≠ 国籍** | 雀魂 MahjongSoul 做日麻立直规则，开发方是中国「猫粮工作室/创魂网络科技」 | 不能因为游戏名是中文/日文就判地区，看开发商 |
| **母子结构混判** | GungHo America（美国子公司，母公司日本）、Marvelous Europe（英国子公司，开发方西班牙）、BANDAI NAMCO America（美国子公司，开发方 Counterplay 美国）、Yoozoo Singapore（中国母公司） | 冲突时按你要回答的问题选层，并写清依据 |

## 写入安全（v10/v17 新增）

| 坑 | 现象 | 解法 |
|---|---|---|
| **`is_deleted` 墓碑造成重复 key** | live 文件有 `{"key":"user-collections.uc-xxx","is_deleted":true}` 条目，**无 value 但 key 开头匹配**。原样带上会与新建集合 id 撞车，`AssertionError: 存在重复 key`（实测 C-Z97 撞了） | 载荷生成器读 live 时有 `dropped_tombstones` 分支丢弃 |
| **改名后新旧名并存** | 厂商集改名后旧名在基线已不存在 → 被「基线外 live 集合」逻辑当成要保留 → 客户端出现重复集 | 维护 `RENAMED = {旧名: 新名}` 显式映射，旧名不进载荷 |
| **变更层键名各轮不同** | 校验器的 `LAYERS` 漏一层 → 正常来源集全被报「意外」 | 各层键名：`真命中`(v9/10/11) / `新建收藏集[].真命中`(v12) / `迁移计划`(v13/14) / `吸收迁移`(v17) / `迁移`(v18)。**必须列全** |
| **短码 vs 全名** | 变更层存短码 `C-N25`，集合名是全名 `"C-N25 厂商-New Reality Games"` | 统一 `n.split(" ",1)[0]` 取短码再比。写成 `n.startswith(s)` **方向会反** |
| **改名被误报为移除** | 改名 = 一增一删但成员不变，不识别就报「移除了收藏集」 | 维护 `RENAME` 白名单，把改名对从「实质增删」剔除 |
| **备份清理只删一半** | `glob(prefix+'*')` 按 mtime 排序后删 `fs[1:]`，两文件 mtime 略有差异 → 误删 json 只留 csv | **只 glob `.json`**，删除时 `.replace('.json','.csv')` 删配对 |

## 基线迭代（v13–v19 新增）

| 坑 | 现象 | 解法 |
|---|---|---|
| **自迭代重复叠加变更层** | 生成脚本读上一版基线 + 叠加变更层，第二轮把上轮迁移再做一次 | 检测基线是否已含本轮特征（如已含 `C-Z96`）→ 自动回退 `_原始快照_` 重放 |
| **重放时 CSV 读错目录** | 快照 JSON 无成员明细（走 CSV 重建），CSV 必须读**快照目录下**的，否则拿到上一轮结果 → 成员重复计入 | 快照 JSON 与 CSV 同目录，配对读取 |
| **重跑分类脚本冲掉人工判定** | `_v7_classify.py` 整体重写判定文件 → 收藏集从 219 掉到 213、13 款未归类 | 重跑后与备份**合并**（人工判定为基底，auto 只补基底没有的 key） |
| **整组统计被逐个 del 破坏** | 检测厂商被掏空时边遍历边 `del`，漏判兄弟成员（实测 4 款只拦下 1 款） | 先收集 `hollow = [...]`，再整组处理 |
| **扫描扫出假「未归类」** | `library_tags.json` 含未拥有条目 | 扫描**必须以基线成员集合为真实库边界**，取交集 |
| **appid 类型不一致导致假「未归类」** | 成员数组里 appid 混存 `str` 与 `int`。用 `mem['123456']` 查不到实际以 `123456`（int）存放的成员 → 误报漏归类，且**反复误判**（连续两次给出相反结论） | 任何入 dict 的 ID **先 `str()` 归一化**：`mem = {str(a): name for ...}`。写入基线前也统一转 `str`。实测某基线 3991 个成员中有 16 个是 int，且**全部来自迁移轮次新增** |
| **同名公司不同国** | 上海 `Gamera Games`（现 Gamirror）与意大利 `Gamera Games Srl`（Gamera Interactive母公司）**毫无关系**，缩写只差一个字母 | 厂商名匹配必须含**注册地或法人全名**；查证时优先权威企业库，MobyGames 等会主动标注 "Not to be confused with..." |

## 地区语义类目扩展（v19 新增）

| 坑 | 现象 | 解法 |
|---|---|---|
| **只看 Z 兄弟类会漏掉错位项** | 放宽 Z97/Z99 地域口径时，只从 Z95/Z96/D 迁移，**本就错位在 Z97/Z99 里的日韩游戏**（如 Blue Archive / NEXON、Wuthering Waves 旁的韩系手游）被完全漏掉 | 放宽口径必须处理**三类**来源：Z 兄弟类 / D 类 / **本就在目标类里的错位** |
| **联网轴有历史偏差** | category ∈ {20,27,36,38} 判联网，实测某库 Z97 的 81 款有 15 款未命中、Z99 的 182 款有 6 款命中，约 19% 偏差 | 它是**启发式不是铁律**，大批量迁移前先抽查未命中/命中名单 |
| **改名与内容冲突** | 把日韩游戏放进「C-Z97 厂商-**中国**联网游戏」→ 名称与内容不符 | 先定方案：改「东亚」/ 改「CJK」/ 另建 C-Z98 给日韩。编码永不重排 |
